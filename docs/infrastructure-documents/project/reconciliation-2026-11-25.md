### 7. CI cross scope renames: source level risk, confirmed in the code, not reproduced

Status: open. Evidence: runner/tools/ci_scope.py, function changed_paths, runs plain `git diff --name-only before after`. Git's default rename detection means a renamed file reports only its destination path, so a rename of executable code into a documentation path would present to the classifier as a documentation change, and the docs only routing in .github/workflows/build.yml would then skip the test, build and proof jobs for a change that removed code. The fail safe half of the design stands: when the range cannot be read, changed_paths returns None and decide answers false, which runs the full build. No test in the classifier's test files pins rename behaviour; I searched them and found no rename case. No incident is established: this is a reading of the source, not a reproduced bypass. Owner: Muse, CI lane. Next step: pin a rename case in the classifier tests first, then decide whether changed_paths should read both sides of a move (name status output, or rename detection off) while keeping the fast prose only handling and the unreadable range fail safe.

### 9. Switch proof fixture and capability provenance: hypotheses, not reproduced

Status: unknown. Evidence: a source reading of runner/tools/switch_proofs.py. In run_roster, each entry's outcomes are looked up by the ids of the tests that were loaded for it. A class or module setup error is reported by the test framework under a holder id that is not one of the entry's own test ids, so those tests would carry no outcome at all. For an entry whose tests all sit in the failing class the verdict reads SKIPPED, which is safe. For a mixed entry, tests from more than one class where one class's setup fails and the other's pass, the verdict would read proven on the smaller passed count, with the failed class's tests silently absent. I did not build the broken setup fixture in this pass, so this stands as a supported hypothesis, not a finding. The capability half: the set of capabilities a leg declares is taken as given by the caller of run_roster, and nothing in switch_proofs.py validates a declared capability against a dedicated check; whether the hosted root legs were ever affected is not evidenced either way. Owner: Muse, switch proofs lane. Next step: build the deliberate broken setup fixture, record the verdict it produces, and separate verified, declared, failed, inapplicable and unknown outcomes in the rendering.
