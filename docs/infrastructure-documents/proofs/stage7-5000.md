# Stage 7 — P1 at 5,000 characters

This is the record of the gate property family checked at a
script bound of 5,000 characters: P1(5000), the nine clauses
of `properties.md` for every handling whose script has at
most 5,000 characters. The stage names now follow the ladder
one rung at a time — stage 6 closed at the 500-character
bound — so the 5,000 rung is a stage of its own here, with
its own run and its own record.

`stage6-cap.md` recorded this rung as the same searched set
as the re-run at the production cap, and gave the reason:
the character count is not a state variable, `Init` admits
the same cross product at every bound, and no step of `Next`
branches on a script's length or its text. That argument
stands, and this stage does not replace it. What this stage
adds is the run itself at the 5,000 bound, so the rung's
claim rests on a check run at its own bound and not only on
the argument that the check would come out the same.

## How the bound was set for this run

The bound is a declared interpretation in `Gate.tla`'s
header, not a configuration constant and not a state
variable — `stage6-rung500.md` sets out why. The copy of
the model on `main` keeps the production-cap declaration,
P1(1048576), which subsumes this rung. For this stage's
check, a scratch copy of the model was taken whose header
declares the 5,000 rung, P1(5000), and whose
`GateEnforce.cfg` comment names it. The scratch copy was
diffed against the tree copy before the run: the difference
is the header comment and that one configuration comment,
and nothing else. No action, invariant, or message field
differs. `Claim.tla` and the remaining configurations are
unchanged from the tree.

TLC 2.19, each run exhaustive, on Java 21. Every run starts
from 786,432 initial states, and the depth of each gate
search is 18, as at the earlier rungs. The fingerprint
collision estimates TLC printed were on the order of 1e-7
to 1e-6.

The counts match the 49, 500, and cap rungs exactly, as the
same-searched-set argument said they would. What the rung
changes is the set of real handlings the graph stands for:
at this bound it stands for handlings with scripts of at
most 5,000 characters, and `P1Inv` holding over the searched
set is, at this rung, P1(5000).

## The two counterexamples that are supposed to exist

Both witness configurations were run at this bound, and
both fail in the shapes they are supposed to fail in.

`GateWitness.cfg` (`NothingExecutes`, audience enforce)
fails with a counterexample ending at `outcome = "execute"`
for a message that is signed, encrypted, fresh, within both
caps, addressed to this runner, with a free claim and no
cancel — 3,095,425 generated, 2,308,999 distinct, the same
as at the earlier rungs. The strong form still lets a good
job through.

`GateDefaultWitness.cfg` (`AudienceWasRequired`, audience
off) fails with a counterexample ending at
`outcome = "execute"` with `audienceOk = FALSE` and every
other clause holding — 3,106,561 generated, 2,320,141
distinct, the same as at the earlier rungs. Clause 4 is
still vacuous in the default form, and still checked for
real under enforce, where it holds.

## The conformance family after the check

`runner/tests/test_proof_constraints.py` runs 67 tests, all
passing, and `runner/tests/test_proof_conformance.py` runs
64 tests, all passing; `runner/tests/test_skip_registry.py`
runs 5 tests, all passing. The check changed no runner
behaviour and no model file on `main`.

## What this does not say

P1(5000) holding says nothing new about the rungs above it;
each named stage is checked when its turn comes, in the
ladder's order. The model's scope is otherwise the first
rung's scope: the mail path, the surfaces named in stage 2,
and the cryptography assumed, not proven, as `readme.md`
states. The standing challenge in `thinking.md` is
unchanged by this rung: the model argues a script's content
cannot move the gate from the code's check order, and a
demonstration over every constructible script at the bound
remains a different, stronger artefact that this work has
not produced.
