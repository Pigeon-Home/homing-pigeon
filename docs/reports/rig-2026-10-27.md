# The second rig, 2026-10-27

Muse operates this box. Grok set it up and does not. It is a
Hetzner Cloud virtual machine in Nuremberg (`nbg1`), held so
the campaign can keep growing while a hosted runner polls the
Cloudflare queue on the same machine. The address is not in
this file. The root password is not either. The account name
on the Worker hostname is not either. The conductor gives
Muse those out of band.

## The machine

| | |
|---|---|
| Provider | Hetzner Cloud |
| Location | Nuremberg, `nbg1` |
| Hypervisor | KVM, full virtualization |
| CPU | 1 vCPU, AMD EPYC-Genoa, 1 thread |
| Memory | 917 MiB |
| Disk | 19 GB, 1.3 GB used, 17.7 GB free |
| OS | Fedora Linux 44, x86_64 |
| Python | 3.14.7 |
| Tree on the box | `main`, fetched at the start of every grow |

Two long-running processes share it, and they do not share a
copy of the code.

The hosted runner is `homing-pigeon.service`. It starts
`/root/.homing-pigeon/runner.py` with the config beside it.
`hosted` profile, poll 20 s, outbound only. Updating the
fuzzer does not touch this copy.

The campaign process is `hp-dedust.service`. It runs
`/opt/hp-rig/grow.sh` with its working directory
`/opt/hp-rig/homing-pigeon`, a clone of the public repo.
systemd starts the script again ten seconds after it exits,
including after a reboot. `Nice=5`. `MemoryHigh=480M`.
`MemoryMax=640M`, so a runaway grow is killed before the
runner. The log is `/var/lib/hp-dedust/grow.log`, cut back
at 50 MB.

Each start fetches `origin/main`. If the copy is behind, it
resets to `main` and drops the corpus grown on the old tree.
If the fetch fails, it grows whatever is on disk. Then one
target, `--jobs 1`, for 30 minutes, up to 20,000 rounds. The
archive stays in `/var/lib/hp-dedust`, capped at 8 GB, oldest
deleted first. The box does not push and it does not bank.
`/opt/hp-rig/run` is a one-off test, and its result stays on
the box too.

The box has one core, so one target. Do not stop the grow to
leave the core idle. Do not add a second writer.

The samples below are from earlier the same day, including a
stretch when the grow had been stopped. They are the record of
that stretch. They are not the current order.

## The Cloudflare queue

The pipe is the Worker's own Durable Object, not Cloudflare
Queues the product. One Worker, one tenant, one SQLite-backed
Durable Object of class `TenantQueue`, binding name
`TENANT_QUEUE`. The migration uses `new_sqlite_classes`. A
free-plan account rejects `new_classes` (error 10097), which
is why the class is SQLite. `compatibility_date` is
`2026-10-25`. `keep_vars` is on, so a deploy does not delete
the dashboard secrets.

There is no `TENANTS` KV namespace. The tenant record is the
four secrets `TENANT`, `SI_TOKEN`, `RUNNER_TOKEN` and
`HMAC_SECRET`. The slug those secrets name is
`homingpigeon02`. The values are not in this file. The
runner's copy of the HMAC is the key whose fingerprint is
`k-7e1ec001`.

`GET /health` returns `200 {"ok": true}` and does not ask for
a token. Every other call is under `/t/<tenant>/`:

| Who | Call | Gate |
|---|---|---|
| SI | `POST /jobs` | SI bearer, then HMAC-SHA-384. 202, or 200 if that id is already queued |
| SI | `GET /results`, `POST /results/<id>/ack` | SI bearer |
| runner | `GET /jobs`, `POST /jobs/<id>/ack`, `POST /results` | runner bearer |
| anyone | a slug that is not the secret | `404 {"error":"unknown tenant"}` |
| anyone | the right slug, wrong or missing bearer | `401 {"error":"runner token"}` or `{"error":"si token"}` |

The default quota, because no KV record overrides it, is 600
jobs an hour and 256 MiB of envelope bytes a day. Over that
the Worker answers 429 with `Retry-After`. A job body over
4 MiB is 413. A bad signature is 403. A lease lasts
`LEASE_MS`, default 300 seconds. Five failed attempts and the
job moves to that tenant's dead-letter list. The runner does
not ack a job until its result has been posted.

The runner dials the tenant base, leases, and posts results.
Its systemd unit has no `Environment=` line, so the runner
token lives in `transport_queues.token` rather than in
`token_env`. The profile is `hosted`: advisory judge, attested
results, workspace `/data/work`.

One ping has been through it. The SI posted
`67afed13-2d34-4065-8f9e-8571b433d7c3` at 21:03:36 UTC. The
Worker returned 202. The runner logged `kind=ping`, `exit=0`,
and `delivered (attempt 1)` on that same poll. The SI read the
result back: one encrypted envelope (`hp_enc`) naming
`k-7e1ec001`. The longer record of that exchange is
`docs/reports/queues-2026-10-27.md`. At the CPU sample above,
the same runner was still active.
